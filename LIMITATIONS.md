# BIDSvue — Limitations

What the **currently-shipped code** can't do, and why. This document records present-tense behavior, not future plans — items marked **inherent** are architectural trade-offs we accepted; items marked **fixable** have a known path forward but aren't scheduled yet. Scheduled work lives in [ROADMAP.md](ROADMAP.md); active design rationale lives in [ARCHITECTURE.md](ARCHITECTURE.md); per-feature history lives in `git log`.

## Platform coverage

- **Signed installer is macOS arm64 only.** *(Fixable.)* Linux x86_64 and Windows x86_64 bundles are built by GitHub Actions from committed sidecars, but they are unsigned and still require clean-machine smoke before public release. Windows Authenticode signing and any future Linux package signing are separate milestones.
- **`dcm2bids` requires `pip install dcm2bids` on the user's system.** *(By design as of 2026-06-14.)* dcm2bids was previously a bundled Nuitka sidecar (macOS arm64 only); unbundling it dropped ~7.6 MB from the DMG and let users track upstream's release cadence. The wizard auto-detects the system binary on PATH and shows an install hint when absent. BIDSvue still injects the bundled `dcm2niix` on its PATH so a clean `pip install dcm2bids` works without a separate `dcm2niix` install. `scripts/build-dcm2bids-sidecar.sh` is retained in-tree as the round-trip path — to re-bundle for a future release, revert the unbundle commit and the build script's output becomes load-bearing again.
- **`heudiconv` requires user-installed Python.** *(Inherent to the upstream tool.)* The wizard auto-detects it on PATH and shows an install hint when absent.
- **x86_64 macOS is permanently out of scope.** *(Inherent — explicit project decision.)* Apple Silicon is the only macOS target. `bun tauri build` for `x86_64-apple-darwin`, the release script, the CI workflow, ARCHITECTURE.md, and this document all agree. Do not add it to any matrix.

## Format coverage

- **PET importer is DICOM-only.** *(Fixable.)* ECAT (`.v`) deferred to a future M13. Two example cases (SiemensHRRTNRU, SiemensTrioBrainPETFZJ) fail at conversion because bundled `dcm2niix` does not read ECAT. Path forward: port `pypet2bids/read_ecat.py` + `ecat2nii.py` (~509 LOC) to TS, then feed through the existing `enrichPetSidecar` pipeline.
- **MEG importer covers CTF, Elekta-FIF, KIT, BTi.** *(Fixable.)* Other vendors (BrainVision EEG, EDF, others) not implemented. Adding a vendor is a parser module + dispatch entry.
- **MNE-BIDS importer is interpreter-gated and scoped to single-file recordings.** *(Fixable / by design.)* The optional "MNE-BIDS" importer runs the user's **local Python** `mne`/`mne_bids` (0.14–<0.21) over one raw **file** — delegated third-party code execution, distinct from the bundled offline ezBIDS MEG converter. It is shown only when a usable interpreter is detected (Rust probes `python3`/`python`, `py` on Windows, with PATH backfill; a venv that isn't on PATH needs a terminal launch with that env active). v1 covers true single-file formats only — `.fif`, `.edf`, `.bdf`; directory formats (CTF `.ds`, KIT, BTi) and companion-file formats (`.vhdr`, `.set`) are deferred. When a ranked events sibling (`<stem>-eve.fif`/`.eve`/`-eve.txt`) is detected, the wizard shows a code→name table and **blocks the import until every code is named** (no partial naming); a raw with no events file converts without `event_id` (valid BIDS). Imports go into an **empty destination only** (the staging tree is merged via the reversible OperationContext + `recordCreatedTree`, so it's undoable from History; a non-empty destination is refused). When the interpreter is missing or out of range the importer is shown greyed with an install/upgrade hint rather than hidden. A mocked action-layer end-to-end test is still a follow-up (the conversion is verified against real MNE sample data).
- **Native DataLad engine (`datalad-rs`, reported in-app as `bidsvue-annex`) supports a subset of git-annex special remotes.** *(Fixable.)* Covers `SHA256E` / `MD5E` / `SHA512E` keys, the S3 `exporttree=yes` remote (all OpenNeuro datasets), the `web` special remote, AND the public-RIA `ria+http(s)://` layer (M-DL15 shipped 2026-06-15). Fetch verifies the content hash for `SHA256` / `SHA256E`, `MD5` / `MD5E` (every OpenNeuro dataset — added 2026-06-28), and `SHA512` / `SHA512E` keys; `SHA1*` / `WORM` / `URL` keys are surfaced as "backend not supported" (SHA-1 is legacy and not a direct dependency; WORM/URL aren't content-addressed). Encrypted-S3, `ria+ssh://`, gcrypt, datalad-archives, external-helper, tahoe, glacier, bup, and bittorrent remotes are surfaced as "unsupported" by `datalad_native_probe` with a `RemoteVerdict.reason`. The Preview pointer card surfaces that reason via the per-dataset capability cache AND StatusBar's "Fetch all pending" affordance is capability-aware (full M-DL10 closure shipped 2026-06-15).
- **Native `update` refuses fast-forwards that change submodule gitlinks.** *(Fixable.)* M-DL12 (2026-06-15) ships `update_dataset(root, remote_name?, should_interrupt)` for fetch + fast-forward against a configured remote. When the upstream tree adds, removes, or advances a `EntryKind::Commit` (submodule gitlink), update refuses with a typed `[refusal=submodule-changed]` token and points the user at `git submodule update --recursive` or a recursive re-clone. Real DataLad datasets DO advance subdataset gitlinks as normal history; until a follow-up commit teaches `update_dataset` to also rewrite the submodule worktree per `.gitmodules` + bump `.git/modules/<name>/HEAD`, BIDSvue blocks the whole update rather than half-applying. The escape hatches always work outside BIDSvue.
- **Native `update` refuses diverged history, dirty worktree, dirty index, and pathological trees.** *(Inherent to the milestone scope.)* Force-pull is out of scope; users who genuinely want to overwrite local history run `git reset --hard origin/<branch>` outside BIDSvue. Dirty-index check (audit round 3 P2.2) catches the case where the worktree is clean but `.git/index` has staged changes that the fast-forward's index rewrite would silently drop. Submodule-scan depth + tree-cycle caps (audit round 3 security P3) refuse poisoned-upstream pathological trees.
- **Push to upstream is intentionally out of scope for the native DataLad engine.** *(Inherent — by design.)* Publishing changes requires either the Cloud Share modal (OpenNeuro / brainlife / EBRAINS — accessible via the "Share these changes upstream…" link in the Save dialog) or an external `git push` / `datalad push` invocation outside BIDSvue. The renderer has no push button; `bidsvueAnnexRunner` has no `push` method.
- **SSH clones require a working `ssh-agent` or `~/.ssh/id_*` key on the host.** *(Not fixable inside BIDSvue.)* M-DL16 transport-layer closure (2026-06-14) added `ssh://` + SCP-form `user@host:path` to the clone URL allowlist. The underlying transport spawns the host `ssh` binary inheriting `$SSH_AUTH_SOCK`. BIDSvue never prompts for passwords, stores private keys, or generates keypairs. The Tauri main process scrubs `GIT_SSH` / `GIT_SSH_COMMAND` / `GIT_SSH_VARIANT` / `GIT_PROXY_COMMAND` at startup, so a hostile launcher cannot redirect the spawned ssh; `SSH_ASKPASS=/usr/bin/false` plus `SSH_ASKPASS_REQUIRE=never` defuses forced askpass, and `DISPLAY=""` is also set at startup on non-Linux platforms. Linux keeps `DISPLAY` for GTK WebView startup and relies on those askpass pins plus per-spawn child env scrubbing. If `SSH_AUTH_SOCK` is unset and no key is loaded, the spawn fails with a clear transport error — users resolve it via the OS (`ssh-add`, `~/.ssh/config`, accepting the host key with `ssh <host>` once outside BIDSvue). Password-in-URL stays rejected on every scheme.
- **`ria+ssh://` URLs are rejected pending SSH-RIA support.** *(Fixable.)* Public `ria+http(s)://` shipped in M-DL15. The SSH URL parser accepts `ria+ssh://user@host/store/dataset-id` for classification, but clone/fetch refuse it because SSH transport and RIA store layout are separate layers. Plain `ssh://user@host/path` clone works today.
- **The native engine fetches annex content from S3 / web / public-RIA special remotes only.** *(Inherent — scope decision.)* `bidsvueAnnexRunner.get()` covers `S3 exporttree=yes` (every OpenNeuro dataset), the implicit `web` remote, AND the `ria+http(s)://` layer (M-DL15 shipped 2026-06-15). SSH-based annex content fetch (`git-annex copy --from <ssh-remote>`) is intentionally out of scope; M-DL16 ships SSH for the **git transport** (clone + M-DL12 native `update`) only. `ria+ssh://` parses for classification but the fetch loop refuses.
- **BIDS-MEG schema has no token for the 4D / BTi head frame.** *(Inherent to BIDS schema.)* The parser emits `MEGCoordinateSystem: "Other"` with a descriptive `MEGCoordinateSystemDescription`. Forward-compatible.
- **Reproin physio rescue (Pass 1b) skips multi-session subjects.** *(Fixable, mirrors upstream `reproinx.py` defer.)* `*_recording-*_physio.{tsv.gz,json}` files emitted into `<root>/derivatives/scanner/<sub>/.../func/` are promoted into the main BIDS tree only for single-session subjects (the rescue injects `_ses-Y` deterministically); multi-session subjects need acquisition-time matching against the corresponding `_bold` JSON sidecars to pick the correct session, which is not yet implemented. The orchestrator's H1 safety gate counts skipped physio files per root, surfaces a per-root entry in the import wizard's `failures[]` panel explaining why derivatives were preserved, and tells Pass 4 (`dropDerivatives`) to spare those roots so the physio data isn't silently deleted. Multi-session physio users see the files in `derivatives/scanner/`; single-session users see them in the canonical BIDS location.
- **MRSI / spatial spectroscopy has no viewer.** *(Fixable.)* NIfTI files with complex datatype (`DT_COMPLEX64` 32 / `DT_COMPLEX128` 1792 / `DT_COMPLEX256` 2048) AND spatial extent (any of `dim1`, `dim2`, `dim3` > 1) route to the file-info card via `probeNiftiKind` returning `'file-only'`. The 1-D NIfTI-MRS signal reader cannot represent a CSI volume meaningfully, and building MRSI UI against the single one-sided dev fixture (`mrsi.nii.gz`, no sidecar) would over-fit. Unblocks when a BIDS fixture with the `.nii.gz` AND a `.json` sidecar carrying `SpectrometerFrequency` / `ResonantNucleus` / spatial transform lands. The single-voxel SVS path (`dim1=dim2=dim3=1, dim4>1`) is fully wired.
- **SVS viewer has no editable peak annotations or phase / apodize / component controls.** *(Fixable.)* `SpectroscopyViewer.svelte` hardcodes NAA 2.0 / Cr 3.0 / Cho 3.2 and locks the upstream demo defaults (`mode='real'`, `phase0=0`, `phase1Ms=0`, `apodizeHz=0`) so the control row stays a single line. A Preferences-pane peak editor and an "Advanced" disclosure for phase / apodize / component selectors are tracked in ROADMAP.md "Wishlist > Spectroscopy viewer follow-ups". SVS files paired with anatomy do NOT show the upstream demo's "MRI + MRS + voxel" scene — different SVS scans may sample different voxels, BIDS does not encode the pairing, and faking it would mislead.
- **TSV editing is alpha.** *(Shipped 2026-05-18, post-v0.1.)* `participants.tsv` + `*_events.tsv` + `*_scans.tsv` + `*_sessions.tsv` + `*_channels.tsv` are cell-editable via `TsvEditor`, with add/remove rows + columns and a fill-column affordance. Out of scope today: Save…-to-siblings broadcast (TSVs aren't shared the way JSON sidecars are), column-type inference, participants.json schema integration, HED tagging, virtualisation (the editor falls back to a read-only `<pre>` view above `header×rows = 10_000` cells to keep WebKit responsive). `participant_id` cells are locked in `participants.tsv` and row deletion is refused while the matching `sub-XXX/` folder still exists — use the entity-rename engine to change subject IDs.

- **Volume + spectroscopy viewers prefer WebGPU, fall back to WebGL2.** *(Resolved 2026-06-30.)* The viewers import the universal `@niivue/niivue` entry, whose `attachToCanvas` tries `["webgpu","webgl2"]` and falls back to WebGL2 when the WebView exposes no WebGPU. macOS WKWebView keeps WebGPU; the Linux WebKitGTK WebView (no WebGPU) renders via WebGL2. The trade-off vs. the earlier `@niivue/niivue/webgpu`-only dist (2026-06-17, ~170 KB lighter) is a larger lazy NiiVue chunk that carries both renderers — accepted so the Linux build is usable. If the macOS DMG bundle size regresses materially, re-introduce a build-time backend switch (keep `/webgpu` for the notarized macOS DMG, universal for Linux/dev) rather than reverting to WebGPU-only.

## Behavior caveats

- **The file watcher rescans + revalidates on every debounced event.** *(Inherent to the snapshot-driven validator.)* 800 ms debounce coalesces rapid edits; the scanner's per-call abort handles partial overlap. Trade-off: higher per-event cost for accuracy.
- **External `chmod`/ownership changes don't refresh read-only lock chips until the next content edit.** *(Inherent to the Linux watcher filter; fixable.)* To break a Linux inotify feedback loop (the scan's own reads bump atime → re-fire the watcher → rescan → loop, which flickered the whole UI), the watcher (`src/lib/state/datasetWatcher.ts`, `isContentRelevantKind`) drops all `metadata` events. Linux `IN_ATTRIB` carries no sub-type, so atime and `chmod`/`chown` are indistinguishable there — permission/ownership changes made OUTSIDE BIDSvue therefore won't update the tree's read-only chips or Save gating until a content/create/delete/rename event triggers a rescan (or the dataset is reopened). Not a data risk: the save path is independently mode-guarded, so a stale "writable" chip still fails the write closed. Follow-up options if freshness is wanted: scan with `O_NOATIME`, or split tree-state rescan from validator rerun. (macOS FSEvents is unaffected — it never reported the atime events, so the loop never occurred there.)
- **Defacing writes one file into the dataset.** *(Inherent.)* The pristine NIfTI is mirrored to `<dataset>/sourcedata/<sub>/anat/…` so revert and re-deface are byte-exact. Every other state stays under app-data — the dataset remains otherwise bit-clean.
- **The CPU deface sidecar runs single-threaded.** *(Inherent to the notarized macOS bundle.)* macOS `niimath` is built `OMP=0 ZSTD=0` because the OpenMP / zstd Homebrew dylibs are signed under a different team ID than our Developer ID cert and dyld refuses them in the hardened-runtime bundle. `allineate` (niimath `-deface`, 12-DOF affine) is the slow path (~23 s on an M4 Max); `mindgrab` (WebGPU) remains the high-throughput alternative.
- **A single native deface call cannot be cancelled mid-run.** *(Deferred.)* `run_deface_process` uses `Command::output()` — no streaming cancellation or output cap — which is acceptable for a short single-shot CPU job. The Batch Deface dialog owns cancellation at the file-loop level (it stops launching new files), so a long batch is still interruptible between files.
- **Undo history doesn't follow a dataset across machines.** *(Inherent to the M6 app-data state move.)* Cross-machine undo would require either embedding state in the dataset (rejected) or replicating app-data via the user's own sync.
- **Reproin operation history is keyed to the study home, not the discovered BIDS root.** *(Fixable.)* For reproin's `<destDir>/<StudyDescription>/sub-*` layout, the import op binds state to `destDir` but the auto-open lands on the discovered descendant. `View > Operation history…` reads from the wrong app-data dir on multi-root imports. Pairs with the v1.1 `ImportOutput` refactor scheduled in ROADMAP.md.
- **Updates are manual DMG re-downloads.** *(Inherent for v0.1.)* The app makes no outbound version check. Auto-updater was wired during Day-4 and reverted same-day because the build-time minisign signing flow proved too fragile to ship in the v0.1 critical path. PRIVACY.md says so. Redo scheduled for v0.2.
- **Physio overlay requires NiiVue rc.8+ features.** *(Resolved 2026-07-01.)* M-PHY1's `viewer.loadSignals(...)` / `removeAllSignals()` / `setSignal(...)` calls require `@niivue/niivue` 1.0.0-rc.8 or newer. As of 2026-07-01 the dep is pinned to the npm-published `1.0.0-rc.10` (was a `file:../mono/packages/niivue` sibling build during M-PHY0), so a fresh clone / CI runner resolves it from npm with no sibling checkout, the `@niivue/dev-images` `overrides` entry and `bunfig.toml`'s `linker = "hoisted"` workaround are gone, and the release-script `file:`/`link:` gate is satisfied.
- **Brainlife cloud-share refuses candidates larger than 256 MiB.** *(Fixable.)* `brainlife/upload.ts` builds the per-candidate tar.gz in WebView memory before the POST. Peak renderer memory is 3-4× input bytes (read buffer + tar buffer + gzip buffer + fetch/request buffering); the 2026-06-12 audit traced an over-cap candidate to potential WebView OOM past 4 GiB and lowered `MAX_BRAINLIFE_CANDIDATE_BYTES` from 1 GiB to 256 MiB to keep worst-case headroom around 1 GiB. The cap is enforced as a pre-loop preflight that refuses oversized candidates BEFORE any remote noop/task allocation, with a clear error pointing users at the brainlife web UI as the workaround. The cap lifts when the Rust streaming tar builder lands (tracked in ROADMAP "Cloud share — brainlife"). OpenNeuro and EBRAINS are already streamed via Rust and have no equivalent ceiling.

- **Merge refuses a same-person fold when both sides are sessionless.** *(Inherent to v1.)* Folding donor `sub-XX` into recipient `sub-XX` works by adding the donor's sessions; when neither side has explicit sessions there is no non-destructive way to combine them (auto-promoting both into `ses-*` is a v2 option). The collision surfaces in the preview with a clear message; resolve it as **distinct** (renumber the donor) or add explicit sessions first.
- **Merge does not detect acquisition-parameter heterogeneity.** *(Deferred to v2 Harmonize.)* v1 detects subject/session label collisions, file-path clobbers, and metadata field conflicts. It does NOT compare EchoTime/RepetitionTime/etc. across donor and recipient scans, nor cluster Entity Sets into Parameter Groups or relabel `acq-VARIANT…`. Copied sidecars are carried as the donor's own scan metadata. The future "Harmonize" capability owns parameter QA — see ROADMAP §2.
- **Merge undo removes added FILES bit-for-bit but may leave empty directories.** *(Cosmetic, v1.)* Undoing a merge deletes every copied file and restores every edited metadata file to its pre-merge bytes; the now-empty `sub-XX/anat/` directories the copy created are left on disk (the generic write-undo deletes files, not their parent dirs). Re-running the scanner shows no files there; a future created-tree-aware undo would rmdir them.
- **Merge runs no separate validator pass.** *(Inherent to v1.)* The optional post-merge validation surfaces as `not-run` in provenance/report (the report shows this); open the merged recipient to run the normal in-WebView validator. `changedRecipientSubjects` already scopes which subjects a changed-subject validation pass would cover when that pass is wired.
- **Merge's `externalSymlinks` / `rootClobber` policies are not enforced in v1.** *(Deferred — audit 2026-06-28 #4/#5.)* The scanner silently skips non-annex symlinks, so external symlinks in a donor are never copied (effectively `skip`, not the declared `refuse`/`dereference`). Donor root artifacts (`README`, `LICENSE`, `code/`, derivative-root `dataset_description.json`) and non-subject-scoped files are NOT copied — the recipient's identity files win. Only the subject trees + subject-scoped `derivatives/`/`sourcedata/` are merged. Root-clobber resolution (refuse / keep-recipient / copy-as-supplement) is a v2 item.
- **Merge re-reads ALL recipient/donor metadata (incl. `dataset_description.json`) from disk under the lease at apply time.** *(Audit 2026-06-28 P1.1/P1.2.)* Every metadata file the merge rewrites (`participants.tsv`/`.json`, `dataset_description.json`, `.bidsignore`, `*_sessions.tsv`) is re-gathered fresh inside the dataset lease and the plan recomputed; if the reviewable surface (collisions / conflicts / discarded values / clobbers) changed, or a recipient metadata file is now unreadable/malformed, Apply throws `MergeStaleError` and sends the user back to recompute. Data-file copies (binary via `copyInto`, remapped text via `writeNewText`) both stage to a sibling temp then finalize with a no-clobber primitive (`ctx.finalizeNewFileNoReplace` → Rust `finalize_new_file_no_replace_authorized_path`; atomic no-replace move when available, exclusive-create copy fallback otherwise). The exists-check is only a fast-path; finalization is the authoritative guard, so a target that appears between the check and the finalize is preserved, not overwritten — no clobber, and no backup-free child recorded. Donor data-file bytes come from the cached scan (donor is read-only — safe); a full donor re-scan is v2.
- **Merge apply is all-or-nothing from the UI.** *(Deferred — audit 2026-06-28 #9.)* `applyMergePlan` supports cancellation + progress, but `runMergeApply` / `MergeWindow` don't wire them yet. A large merge can't be cancelled mid-copy from the UI (it stays reversible via History after it completes).

- **Task events does not parse vendor stimulus logs.** *(Deferred to v2 — by design.)* The "Create events file" / "Clone events…" affordances author header-only `_events.tsv` files and clone existing ones; they do NOT ingest PsychoPy / Presentation / E-Prime logs and map columns into onset/duration/trial_type. bidscoin + ezBIDS already do this well and the working norm is not to rebuild what those tools do. The `author-events` AI prompt can help a user transcribe timing from a pasted log, but there is no built-in parser. Tracked in ROADMAP §2.
- **New task-events files are header-only.** *(Inherent to v1.)* "Create events file" writes `onset<TAB>duration<TAB>trial_type` with no data rows, and (if none is inheritable) a root `task-<label>_events.json` describing `trial_type`. The bundled validator accepts a zero-data-row events file (recommended-metadata warnings, not a row-count error); the user or the AI fills the rows. No fake `0<TAB>n/a` placeholder event is seeded.
- **Task-events clone is create-only-where-missing and runs no validator pass.** *(Inherent to v1.)* Cloning copies the source `_events.tsv` bytes verbatim into every matching run that lacks one; runs that already have an events file are listed as skipped and never overwritten (no-clobber enforced at the atomic-write layer). The clone does not validate that the source's onsets/durations actually apply to each target run — it is a literal byte copy, appropriate for a shared task design but not for per-run performance data. Opening the dataset runs the normal in-WebView validator.
- **The task-events UI is English-only.** *(Inherent to v1 alpha.)* The context-menu entries (native menu — English-only by project policy) and the clone preview dialog are not localized; only the `author-events` AI prompt has pt/es translations. BIDS data values stay canonical English regardless. Localize the dialog if the feature graduates from alpha.

## Validator caveats

- **`validate()` cannot be hard-cancelled mid-CPU.** *(Fixable, requires Worker.)* Aborts are propagated three ways; the renderer's await returns promptly. The underlying CPU work continues until it naturally completes; its result is dropped by the generation gate.
- **`TauriFileOpener.stream()` buffers full TSV payloads.** *(Fixable.)* The NIfTI rule's `readBytes(1024, 0)` is the load-bearing case and is already lazy. Large `events.tsv` / motion-regressor sidecars hit the unstreamed path. Fix: chunked `stream()` over `FileHandle.read()`.
- **Rust validator backend (default for v0.1) lacks per-spawn cancellation.** *(Fixable.)* `run_bids_validator` uses `spawn_blocking` with no cancellation token, so rapid saves / watcher churn / dataset switches leave stale validator processes running to completion. Generation checks keep stale results from being ingested. JS validator backend has the same characteristic.
- **The `REAL_DATE_IN_SCANS` privacy lint is a best-effort heuristic, not a guarantee.** *(Inherent.)* It flags `acq_time` years > 1925 as real (unshifted) dates. To avoid false positives on the import's OWN `--shift-dates` output (which anchors a subject's earliest scan to 1925 and preserves intervals, so later sessions legitimately land in 1926+), a subject carrying a ≤1925 anchor date has its 1926..1989 rows SUPPRESSED — those are plausible shift-intervals. A `real-modern` date (year ≥ 1990, `REAL_ERA_MIN_YEAR`) is always flagged even with an anchor present (a partial/mixed shift can't reach 1990 from 1925). The gap: a genuinely real OLD date (1926..1989) in a subject that also has a 1925 anchor is suppressed. This is a rare hand-edited/partially-shifted case; the lint is a review-before-share warning, not a blocking de-identification check.
- **Rust validator backend covers the parity slice but isn't byte-identical to upstream `@bids/validator`.** *(Worked around case-by-case.)* The previously-confirmed `*_coordsystem.json` false-positive `SIDECAR_WITHOUT_DATAFILE` is **fixed at the source**: the bundled `bids-validator-rs` (>= commit `0c78cc9`) corrects the association builder (marks resolved targets "viewed", mirroring Deno's walkBack), so BIDSvue trusts the validator's output directly and the renderer-side `dropCoordsystemFalsePositives` shield has been removed — a genuinely orphaned coordsystem now correctly surfaces. If a tester reports a new divergence, the options are a targeted renderer post-process or opting out to the JS backend via `VITE_BIDSVUE_VALIDATOR_BACKEND=js`.

## AI assistant (alpha)

The AI integration is **default-on**: it is compiled into every build (there is no longer an `ai` Cargo feature) and enabled by default. It can be fully disabled at build time by setting both off-switches together — `VITE_BIDSVUE_ENABLE_AI=0` (renderer) AND `BIDSVUE_DISABLE_AI=1` (Rust) — which yields no AI UI and no callable AI Rust surface. Recipes: `bun run dev:no-ai` (dev) / `BIDSVUE_DISABLE_AI=1 bun run release:macos` (no-AI DMG). Read tools and M-AI5 write tools (gated behind a per-write Approve/Reject chip) work in every default build; the write path still has approval-UX gaps tracked before the first AI-enabled notarized DMG (see below).

- **AI is default-on, disable-able via two env vars** *(fixable — set both off-switches).* AI is compiled into every build (the `ai` Cargo feature is gone). To turn it off, set `VITE_BIDSVUE_ENABLE_AI=0` (Vite dead-codes the toolbar tile + `<AIWindow />` mount + About rows — zero bytes) AND `BIDSVUE_DISABLE_AI=1` (`ai::ai_disabled_at_build()` via `option_env!` short-circuits `run_ai_prompt` / `probe_ai_clis` / `--mcp-server`, so even a compromised renderer can't drive the AI surface). Both are needed for a fully-disabled build. **Windows ships without AI** (the MCP control bridge is a Unix-domain socket; `run_ai_prompt` refuses on Windows). See ROADMAP "AI integration follow-ups".
- **Write tools route through the approval-gate control bridge** *(M-AI5 wired; approval-UX gaps remain).* `rename_entity` / `save_sidecar` / `save_text_file` / `delete_file` are surfaced + allowlisted; each call relays over the per-session Unix-domain-socket bridge (peer-UID + bearer auth per Locked decision 13) to the main app, which shows an Approve/Reject chip and only then acquires the `MutationLease` + runs the existing engine (reversible via operations.log). Path authorization is Rust-authoritative at the chokepoint (`.git*`/`.datalad`/`.bidsvue`/`.heudiconv`/`.hg`/`.svn` blocked for read AND write; backslashes rejected). The top-level `derivatives`/`sourcedata`/`code` refusal is Rust-authoritative too (`validate_ai_rel_path` at the chokepoint, for read + every write tool). **Known feature-ON UX gaps before an AI DMG:** the chip shows a path/descriptor, not the proposed bytes/diff (P1.1); no session-scoped pending-write map yet (P1.4/R1.2).
- **Read tools attach to Send when a dataset is open** *(audit 2026-06-22 P1.1 closure)*. When `datasetStore.dataset?.root` is non-empty, `run_ai_prompt` writes a `session-config.json` AND adds `bidsvue --mcp-server <cfg>` to the CLI's argv via `build_argv_with_mcp`. The AI can then call `read_file` and `list_files` against the dataset. With no dataset open, the panel runs as general chat with no dataset access.
- **Direct OpenAI-compatible runtimes are non-streaming in the first pass** *(shipped 2026-06-23).* Ollama and generic OpenAI-compatible endpoints use the same BIDSvue tool definitions, read-egress accounting, and write approval bridge as CLI-backed sessions, but the HTTP path currently calls `/chat/completions` with `stream:false`; the transcript updates when each model response returns. Endpoint URL + model are persisted. Generic API keys are accepted per session only and are not saved. Plain `http://` endpoints are allowed only for localhost; remote compatible APIs must use `https://`.
- **Read tools are `read_file` + `list_files` + the three read-via-bridge tools** *(M-AI13 shipped.)* `read_file` (text 64 KiB / binary 1 MiB caps) and `list_files` (paginated, symlink-rejecting, cycle-safe) re-walk the filesystem in the subprocess. `get_dataset_summary`, `run_validator`, and `get_validator_issues` are renderer-served: they relay over the control bridge to the main app, which answers from `datasetStore` (summary) / `diagnosticsStore` (the CURRENT BIDS-validator results the messages panel shows — NOT a fresh run) and resolves with no approval chip. M-AI4 caps apply renderer-side: `run_validator` truncates its issue list at 128 KiB with a "use get_validator_issues" note; `get_validator_issues({severity, code, limit})` filters + paginates (limit max 1000). The renderer bounds each payload at source (never relies on the post-hoc Rust egress drop). The remaining unadvertised tool is the M-AI12 vendored BIDS-spec snapshot reader (separate deferred milestone).
- **App-state consent toggle plus Codex high-trust opt-in** *(decided 2026-06-22; Codex opt-in added 2026-06-23; consent label corrected 2026-06-27.)* The AI panel's toolbar carries the dataset-state checkbox — "App-state reads" (tooltip: "Allow the AI to read this dataset's BIDSvue state (operations log, undo history, and pending upload records). Does not change which dataset files the AI can read.") — backed by `preferencesStore.aiAllowDatasetStateReads`, default off, read once per Send, inline "Changes apply on your next message." hint. Global-state reads (preferences, trust set, share status) carry no PHI and are **always permitted** — the global checkbox + the `aiAllowAppDataReads` preference were removed by design, and `onSend` passes `allowAppDataReads: true` unconditionally. Per-dataset BIDSvue state (operations.log, undo `originals/`, pending intents) is the flag's scope. The same section also carries `preferencesStore.aiAllowHighTrustCodex`, default off: when a dataset is open, Codex is not auto-selected and cannot start unless this opt-in is enabled. The Rust `run_ai_prompt` command enforces the same rule, so bypassing the renderer cannot silently start an unsandboxed Codex dataset session. Byte-level reads of `originals/` still require per-call approval (M-AI5 bridge).
- **The AI reads dataset files directly when a dataset is open; the app-state toggle does not gate that** *(by design.)* `read_file` / `list_files` read any file under the dataset root (the point of an AI dataset session). The "App-state reads" checkbox only gates BIDSvue's own per-dataset bookkeeping (operations.log / undo originals / pending intents) — and those reads aren't surfaced as live tools yet, so toggling it currently changes nothing the AI does. The label was corrected on 2026-06-27 from an earlier "Identification Visible" wording that wrongly implied it gated identity-bearing dataset files. If a future requirement needs to withhold identity-bearing files (participants.tsv, PHI sidecars) from the AI, that is a separate gate on `read_file`/`list_files`, not this toggle.
- **Conversation history capped at 5 turns / 32 KiB** *(audit P1.2 + P1.4 mitigation).* Full multi-turn via interactive subprocess lands with M-AI5; today the renderer prepends a bounded preamble to each Send. Prompts > 128 KiB are refused at the Rust boundary.
- **Stream output capped at 2000 lines per stream** *(audit P1.4 mitigation; `MAX_STREAM_LINES`).* A runaway CLI emits a synthetic Cancel and reaps cleanly. An over-cap single LINE (no newline) returns `truncated` immediately and cancels — `read_bounded_line` no longer drains to the next newline (that could hang forever on an unterminated line; audit 2026-06-21 P2).
- **Per-session egress cap not yet enforced** *(fixable — `ReadPolicy` refactor scheduled.)* Locked decision 17(e) requires a 64 MiB per-session egress counter; today only per-call caps fire. Repeated chunked reads can still stream the dataset to the provider.
- **Direct-mode egress telemetry is a lower bound** *(deferred — unified accounting.)* In direct-runtime mode the `egress_bytes` telemetry counts only tool-result read bytes; it is a conservative LOWER BOUND on actual provider egress, since the full message history is re-sent to the endpoint each round. Unifying egress accounting across MCP and direct modes is deferred — naively summing both would double-count against the 64 MiB cap.
- **CLI tool-surface isolation** *(closed for M-AI3 bare-chat; depends on CLI vendor behaviour.)* Claude `--tools ""` + Codex `--sandbox read-only` + Gemini `--approval-mode plan` are passed in the bare-chat path. The vendor CLIs honour these flags by contract; a future vendor change that ignored them would re-open the gap.
- **MCP read tools pre-approved at spawn (M-AI4.5)** *(closed; depends on CLI vendor behaviour.)* When a dataset is open, the MCP-wired spawn carries Claude's `--allowedTools mcp__bidsvue__<the ten-tool allowlist: read_file + list_files + get_dataset_summary + run_validator + get_validator_issues + the five write tools>`, Codex's `--dangerously-bypass-approvals-and-sandbox` only after the explicit high-trust opt-in (see the dedicated bullet below — Codex's sandbox CANCELS MCP tool calls, so the bypass is the only config that runs them), and Gemini's `--approval-mode yolo` + `--allowed-mcp-server-names bidsvue-<uuid>` (M-AI4.5b: Gemini's built-in tools are blocked by a Policy Engine default-deny written to `<workdir>/policy.toml`, so yolo only auto-approves our MCP tools). This lets the AI call `read_file`/`list_files`/etc. without the per-call permission prompt that previously blocked every invocation. The server-side `resolve_in_dataset` sandbox + per-call size caps are the load-bearing safety; the CLI's prompt is friction-only here. **Write tools ARE in the allowlist too (decision A)** — in headless mode an un-allowlisted tool is auto-denied by the CLI, so the call would never reach our bridge; allowlisting lets the call through to the control-bridge Approve/Reject chip, which fires DOWNSTREAM of the CLI prompt and is the real user gate. The locked rule is "never a WILDCARD" (`bidsvue_mcp_tool_allowlist_never_uses_a_wildcard`), not "no write tools". Bidirectional parity tests (`allowlist_covers_every_registered_tool` + `every_allowlist_entry_maps_to_a_registered_tool`) fail if a tool is added to `mcp/tools.rs` without updating `BIDSVUE_MCP_TOOL_ALLOWLIST` OR a typo lands in the allowlist.
- **Codex dataset sessions are high-trust and blocked by default (2026-06-23 opt-in)** *(Codex limitation, not fixable in BIDSvue.)* Codex's headless `codex exec` **cancels every MCP tool call under any sandbox** (`read-only`, `workspace-write`, `--full-auto`), even with `approval_policy=never` — verified empirically with a trivial probe MCP server (all sandboxed modes return "user cancelled MCP tool call"; only `--dangerously-bypass-approvals-and-sandbox` runs MCP tools). So a dataset-bound Codex session can only run with the bypass, which **also unconfines Codex's own built-in shell** (it can read/write/run on your machine freely). BIDSvue now blocks this path by default in both the selector and Rust command boundary; enabling "Allow Codex dataset sessions to run in high-trust mode" is an explicit trust decision. Consequences after opt-in: BIDSvue's MCP **write** tools still route through the Approve/Reject bridge, but Codex's *own* shell does NOT — a misbehaving prompt could have Codex edit files outside BIDSvue's approval + undo. The trust level equals running `codex --dangerously-bypass-approvals-and-sandbox` yourself in a terminal. **Bare-chat Codex (no dataset) keeps `--sandbox read-only`** so its shell stays confined. **Claude is the confined alternative** for dataset work — it runs the same MCP tools via `--tools "" + --allowedTools` with no sandbox conflict. **Gemini is also confined** (M-AI4.5b): its dataset sessions run `yolo` but a Policy Engine default-deny (`<workdir>/policy.toml`) blocks every built-in shell/file tool even under yolo — verified empirically (a `decision=deny` rule blocks them while our MCP tool still runs; note `tools.core:[]` does NOT block built-ins). So unlike Codex, Gemini's own tools cannot touch the filesystem outside BIDSvue's bridge.
- **Hardened-runtime FD-plumbing notarized-DMG smoke: PASSED** *(2026-06-22.)* The grandchild-spawn + control-socket + telemetry round-trip was validated end-to-end from an installed notarized DMG (open dataset → AI panel → "summarize this dataset" returns data → approve a sidecar edit → derivatives write refused), not just the dev-mode `examples/hello_mcp.rs` handshake. Re-smoke an AI-enabled DMG before a **public** AI release, since the AI/trust path has changed since.
- **Privacy disclosure is a per-runtime line, not yet a per-account one** *(Locked decision 14, partially shipped 2026-06-22.)* Dataset contents read by the AI flow to the selected runtime as tool-call results. The MCP server subprocess has no outbound network of its own, but the spawned CLI or direct HTTP runtime does. The AI panel surfaces this as the always-visible header subtitle under the "AI assistant" title: cloud/generic runtimes say "Files the AI reads are sent to {provider}."; Ollama says the reads stay on this machine. The generic OpenAI-compatible base URL is a data-egress target, not just a model label. The subtitle shows even in bare-chat with no dataset bound — a deliberate, conservative over-disclosure, since typed prompts also reach the selected runtime. Still deferred: the per-**account** identity (which logged-in vendor account receives the data — most runtimes don't expose it to us) and recording the exposed-data classes in the AI-session op-log entry.

## Security limitations

The v1 release closed every must-fix item identified through round 28 + the post-Day-3 P1 sweep. Remaining items below are accepted trade-offs in the currently-shipped code; the corresponding planned hardening lives in ROADMAP.md.

- **Symlink-aware canonicalization on the trust boundary.** Lexical containment via `Path::starts_with` is rejected for `..` / `.` components, but a symlink under a trusted root pointing outside it would currently pass.
- **Token single-use enforcement.** Tokens are reusable within the 5-minute TTL.
- **Trust-set schema is flat path array.** No purpose / createdAt / lastUsedAt metadata. Roadmap item: typed schema.
- **Operation-log paths are absolute.** Needs a log-format migration before path-portability lands.
- **PET metadata operator overlay is unrestricted JSON.** No allowlist / schema validation.
- **Path normalization at the lease boundary is best-effort.** A caller passing a syntactically-different path could bypass a lease.
- **TS-side `validateImportPath` is POSIX-only.** Rust re-validates per-path absoluteness so this is not load-bearing today; relevant for the cross-platform port.
- **`atomicWrite`'s `isUnderRoot` check doesn't resolve symlinks.** Defense-in-depth, not load-bearing.
