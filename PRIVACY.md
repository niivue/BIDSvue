# BIDSvue Privacy Statement

BIDSvue exists so you can convert, deidentify, and curate neuroimaging datasets locally — on your own machine, without sending data anywhere. The app has no telemetry, no analytics, no crash reporter, and no in-app update check. Dataset bytes and the operation history derived from them stay on disk; per-dataset state lives under your OS application-data directory (on macOS: `~/Library/Application Support/com.neurolabusc.bidsvue/`). The only in-dataset write is the M7 deface sourcedata mirror, which keeps a pristine copy of every defaced volume so undo and re-deface stay byte-exact. Note that the machine-local operation history can contain dataset-derived values: a **Merge** that resolves a `participants.tsv` / `*_sessions.tsv` conflict records the raw discarded cell value (which can be age, date of birth, or other re-identifying table data) in that dataset's `operations.log` so the merge stays auditable and reversible. This stays under your application-data directory and is never written into the dataset itself — the dataset's own durable merge record (`sourcedata/bidsvue_merge_provenance.json`) is redacted of those raw values.

The only outbound calls BIDSvue makes are ones you start: clicking **Help > Report an issue…** opens a prefilled GitHub Issue URL containing the diagnostic report (versions + capability flags; no dataset paths or contents — preview it via **Copy diagnostic report** in About); **Help > What's new** and **Project on GitHub** open release/repo pages in your browser; the Launch screen's **Clone DataLad dataset…** action issues HTTPS / SSH `git` traffic to the URL you provided via the in-binary `datalad-rs` engine (reported in-app as `bidsvue-annex`; no `datalad` CLI is spawned and no Python is invoked); the per-file cloud chip's fetch button issues HTTPS GETs to the URLs encoded in the dataset's own `git-annex` branch (S3 `exporttree=yes` and `web` special remotes); the Share modal uploads to brainlife / OpenNeuro / EBRAINS only when you click Upload.

The AI assistant is the one feature that can send dataset contents off your machine, and it only does so when you use it. When you send a prompt, the dataset contents the AI's tools read (file listings, sidecar and TSV text, validator output) plus your prompts and the conversation history leave the machine. There are two modes. In **CLI-spawn mode** (Claude Code / Codex / Gemini), BIDSvue spawns the vendor's CLI as a subprocess and that CLI sends the data to its own vendor cloud — Anthropic, OpenAI, or Google respectively — subject to that vendor's privacy policy. In **direct-runtime mode** (Ollama or any OpenAI-compatible `/chat/completions` endpoint), BIDSvue itself makes the HTTPS POST of prompts, conversation history, and tool results to the endpoint you configure; a local Ollama endpoint is loopback-only so the data never leaves the machine, but a remote OpenAI-compatible endpoint receives it. The AI assistant is compiled into every build and enabled by default, but it can be fully disabled — no AI UI, no AI-related calls — by building with `VITE_BIDSVUE_ENABLE_AI=0` (e.g. `bun run dev:no-ai`) or releasing with `BIDSVUE_DISABLE_AI=1`. With AI disabled, all of the local-only guarantees above hold unchanged.

Optional external tools invoked through BIDSvue (notably `heudiconv`, and the AI CLIs above) are independently developed and may implement their own logging, update checks, or telemetry. Those tools run as separate processes and are subject to their own privacy policies.
